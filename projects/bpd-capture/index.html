Case study · Android + Windows desktop · 2026

BPD Capture: an offline job tracker for a workshop floor

v1.4.2

An Android app, with a Windows desktop version, that I built for Blueprint Digital, the workshop where I work. Every order is tracked by its CE number, from the client's sample through production, dispatch and installation. Photos are filed under the stage they were taken in, each step is signed off by name, and PDF reports are made on the device. It works with no signal and no server.

01 · Brief

What it is for, and what I built

Problem

Job photos taken on a normal phone camera end up mixed with everything else. There is no record of due dates, who signed off a step, or whether jobs finish on time, and reports take manual sorting.

My role

I built it, using Claude Code as my AI coding tool. That covers both apps: the screens, the local database and its migrations, file storage, PDF reports, backups, the update flow, the Three.js logo animation and the safety tests.

What I built

A native Android app (React Native and Expo) and a Windows desktop app (Electron), both in TypeScript and sharing the same CE rules, stages and sync code. Orders move through 4 stages, with 3 production steps, photo capture per stage, work-ticket items, hold reasons and an Insights screen.

Status

Android version 1.4.2, installed directly as an APK (not through the Play Store), plus the Windows desktop app. A sync feature is built but not switched on yet, and release signing hardening is planned.

02 · Architecture

Two apps, one design: a database and one folder per job

On the phone, the screens call a small set of services. All job data goes into a local SQLite database, and photos and videos go into one folder per CE number inside the app's own storage. The only parts that reach the internet are drawn dashed, and each one runs only when the user acts or, for sync, once it is switched on. Every database write notifies the sync engine; with sync off, nothing is sent. The Windows app has the same layout: an untrusted page, a narrow bridge, and a main process that owns the database and the job folders.

03 · Data flow

What goes in, what is checked, where it ends up

Everything a user enters is checked before it touches the database or the file system. A CE number becomes a folder name, so it is cleaned up and the folder it points to must sit inside the app's orders folder. After that, data is only read back on the phone, unless the user sends a report or a backup. 04 · Workflow

One order, from sample to install

Each order moves through the same four stages as the workshop: Sample, Production, Dispatch and Installed. Production is split into the steps the order needs. To move on, someone signs off the current stage or step by name, and the app saves who, when and any notes. That history goes into the PDF report. Both apps use the same stage and step definitions.

Diagram is wide: scroll it sideways.

The person who signs off is filled in for them: the client for a sample approval, otherwise the user chosen on that phone in Settings. Each phone can also be set to a bench, such as Machining or Dispatch, so its job list puts the orders waiting at that bench first.

05 · Security and privacy

What is true today, and what is planned

This describes the current Android and Windows apps. They are tools for one workshop, so the main risks are losing job photos and data, and photos ending up where they should not.

Today

  • TodayOffline-first. The app needs no account and no server to work. Job data lives in a SQLite database inside the app's private storage, and photos and videos live in one folder per CE number next to it.
  • TodayPermissions. Camera, and microphone for sound on job videos. Photo and media access to import from the gallery and to save a backup copy of camera captures. Photo location access is turned off. The app may also install packages, which is used only for the in-app update.
  • TodayWhat leaves the phone. Only what the user sends: a PDF report or daily digest (by email to a saved dispatcher address, or through the share sheet) and backup zips. Checking for an update contacts GitHub only when the user taps the button. There are no analytics or tracking libraries in the app.
  • TodayGallery copy. Camera captures are also saved to a “BPD Capture” album, by design, so photos survive if the app is removed. That copy can be seen by other gallery apps on the phone.
  • TodayInput safety. SQL always uses parameters, never typed text. CE numbers are cleaned up before they become folder names, and every job folder must resolve to a place inside the orders folder. Renaming or deleting a photo cannot reach outside its job. Text in PDF reports is escaped, and a backup restore rejects unsafe zip entries.
  • TodayBackups and updates. A backup can be exported as a zip with an optional password. Before every in-app update the app saves a local backup (keeping the last 3), and Android asks the user to confirm the install.
  • TodayDesktop app boundary. The window runs with context isolation and the sandbox on, and no Node.js in the page. Every file call from the page is checked to stay inside the orders folder, the window cannot navigate away or open pop-ups, and the webcam is allowed only for the app's own page. Data lives in the Windows app-data folder, and the sync token is encrypted by Windows.
  • TodayChecks before release. A script scans the code for SQL built from strings, raw HTML or eval, and hard-coded secrets. Path-safety tests run the real storage code: on a fake file system for Android, and in a temporary folder for desktop, including its window navigation lock.

Known gaps

  • Data lives on one device. If a phone is lost or reset, only exported or gallery copies remain.
  • A backup zip exported without a password is not encrypted.
  • Some build-tool dependencies have open advisories. They are used to build the app, not shipped inside it.

Planned

  • PlannedRelease signing hardening (planned).
  • PlannedSync, switched on. The sync engine is written and tested but turned off. When it is on, each phone or PC signs in with a one-time code approved in the browser, the sign-in token stays in the system's encrypted store, and job data goes to a private repository only.

The device numbers come from an overnight test run on 21 October 2026 on an Android emulator, not a physical phone, so they compare builds rather than describe a real device.

Stack

React Native 0.86 with Expo SDK 57 and React 19, written in TypeScript and built to a native Android app. Data: expo-sqlite in WAL mode with versioned migrations, expo-file-system for job folders. Camera and media: expo-camera, expo-image-picker, expo-media-library, expo-video. Reports: expo-print for PDFs, expo-mail-composer and expo-sharing to send them. Also React Navigation, Reanimated, date-fns, react-native-zip-archive for backups and expo-secure-store for the sync sign-in. The start-up animation is a Three.js scene on expo-gl: the logo's pencil draws the logo, then the colours fill in. Desktop: Electron 44 with electron-vite, Vite 6 and React 19, Node's built-in node:sqlite, and the same Three.js logo animation on its loading screen.

Results

  • Every job's photos, notes, due date and sign-off history sit under one CE number, and can be found by CE number, client or month.
  • A PDF report for one job, or a digest of every job completed that day, is made on the phone and can go straight to a saved dispatcher's email.
  • Android updates install from inside the app, and a backup is always taken first.
  • The same records, CE rules and stages work on a phone and on a Windows PC.
  • A bug where a CE number made only of dots could point outside the jobs folder was found in a security review, fixed, and covered by tests.

Limitations

  • Installed as an APK, not through the Play Store, so each phone is set up by hand the first time. The desktop app is Windows only.
  • Data is not shared between phones and PCs until sync is switched on.
  • Reports go out by email or the share sheet only.
  • Device testing so far: an Android emulator; real-phone testing is limited.

What's next

  • Release signing hardening (planned).
  • Switch on sync with a private repository, so jobs can be shared between phones and the desktop app.
  • Wider testing on more phone models.
